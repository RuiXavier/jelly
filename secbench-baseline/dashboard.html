Static analysis baseline · no taint layer

Jelly × SecBench.js

Plain points-to / call-graph analysis (jelly <entry>.test.js, no -v) run across all 5 official SecBench.js vulnerability classes — 603 real npm-package PoCs curated from Snyk, GitHub Advisories and Huntr.dev. Run 2026-09-04 · Jelly 0.13.0 · Node v26.8.1 · heap cap 8192MB. Goal: establish whether base Jelly is sound and scalable on this corpus before layering taint analysis on top.

Edge count doesn't track module count: the densest graph in the corpus, command-injection/libnmap_0.4.11, produces 54,420 call→function edges from just 67 modules — more edges than mathjs_7.4.0 gets out of 909 modules.

Where it breaks

14 of 603 cases (2.3%) didn't produce a clean result — all traced to two distinct, unrelated-to-Jelly-logic causes.
Root cause, 6 of 6 OOM/crash cases: a single monolithic bundled/dist .js file (tens of thousands of lines, often auto-generated) somewhere in the dependency tree. Module count and overall dependency-tree size don't predict this — monorepo-build_0.1.9 OOM'd at 8GB from just 507 modules, dropping to 538MB/3.3s the moment its one bundled dependency (prettier) was excluded. redos/three_0.122.0 is the near-miss that proves the same point from the other side: only 2 modules, yet 7.4GB / 46s, entirely from one 51,012-line three.module.js.
